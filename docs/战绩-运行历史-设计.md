# 战绩（运行历史）设计

> 目标：给 DICEOMANCER 加一个"过往战绩"面板 —— 像《杀戮尖塔》的 Run History 那样，逐局留档、可回看卡组/遗物/路线/统计。
> 定位：**平台内置模块**（不是单个 mod），因此原版职业与所有 mod 职业都能记录。
> 依据：本文所有游戏侧结论都来自 `Assembly-CSharp.dll` 反编译核对，不是猜测。

---

## 0. 结论先行

1. **游戏自己不留逐局数据**。`CareerStatisticsPackage.AddCampaignInfo()` 只把 `CampaignStatisticsInfo` 累加进 `overallInfo` 与 `classInfos`，累加完就把这一局丢掉 —— 存档里只有"总胜场/最快通关/最高连胜/总击杀"这类聚合值。
2. 但**逐局摘要本身是现成的**：`Career.CampaignStatisticsInfo` 已经带了 20 个字段（种子、日期、职业、胜负、进阶、各类击杀、掷 1/最大/最小次数、检定成败、钓鱼、卡名数组、遗物名数组、被紫雾吞噬次数、游玩秒数）。我们不需要自己去统计这些东西，只需要**在它被丢弃之前抄一份**。
3. 缺的是三样：**逐节点轨迹**（第几个节点、什么类型、当时血量/金币）、**逐层获取**（哪张卡/哪件遗物是在哪个节点拿的）、**展示层**。
4. 采集点只有 5 个钩子，全部是"只读 + 落盘"，不进战斗热路径，不改任何游戏存档。

---

## 1. 参照：杀戮尖塔做了什么

可核对的公开资料（社区整理，非官方文档）：

- **存储**：每局一个文件，按开局时间戳命名（PC 端 `saves/history/*.run`），内容是 JSON；字段包括 `local_time`（本地时间，需要时区转换）、`seed_played` 等，因此"把历史搬到另一台机器"要专门改时区字段。参考社区脚本说明：<https://steamcommunity.com/sharedfiles/filedetails/?id=3379271016>、重建工具仓库 <https://github.com/MufanQiu/sts2-save-rebuild>
- **面板**：一局一行 —— 角色、进阶等级、胜/负、分数、到达层数、日期与时长、种子；点进去是详情。
- **详情**：终局卡组（含升级态）、遗物、药水、每层路线与在每层做的选择（拿卡/篝火/商店），以及分数构成。
- **社区增强**（Run History Plus）：每层耗时、按多种键排序、面板信息更全 —— <https://steamcommunity.com/sharedfiles/filedetails/?id=2802958032>
- **续作改进**（STS2）：鼠标悬停某张卡/某件遗物时，高亮"它是在第几层拿到的" —— <https://www.reddit.com/r/slaythespire/comments/1s6ic7y/>
- **已知代价**：逐局文件会撑大 Steam 云同步（社区里有人因为历史文件堵住云同步而要求关云）—— <https://www.reddit.com/r/slaythespire/comments/1umumcp/>

> 对我们的直接启示：① 逐局一个文件 + 一个轻量索引；② 必须有**条数上限与轮转**，否则会像 StS 一样撑爆云同步；③ "悬停高亮获得层"用**节点快照差分**就能做到，不需要额外数据源。

## 2. 骰子浪游者已有的骨架（读代码）

| 位置 | 事实 | 对我们的用途 |
|---|---|---|
| `Career.CampaignStatisticsInfo : StatisticsInfoBase` | 逐局摘要：`isWin` `className` `playedDate` `seed` `ascensionLevel` `normalEnemySlainCount` `eliteSlainCount` `bossSlainCount` `travelNewNodeCount` `rollTheOneDiceCount` `rollMaxNumberCount` `rollMinNumberCount` `checkSuccessCount` `checkFailCount` `fishCount` `cards[]` `relics[]` `catchByPurpleMistCount` + `playedTimeInSecond` | 记录的"结算半"几乎不用自己算 |
| `Career.CareerStatisticsInfoBase.AddCampaignStatisticsInfo` | 把这些**累加**进生涯总表，不保存逐局 | 证明游戏侧没有逐局历史可复用 |
| `Utilities.CareerStatisticsPackage` | `overallInfo` / `classInfos` / `achievementInfo` / `saveVersion` | 面板可以顺带展示生涯聚合做对照 |
| `Combat.CampaignManager.NewGameLaunchInitialize()` | 开新局时写 `seed = DateTime.Now.Ticks`、`playedDate = "yyyy-MM-dd HH:mm:ss"` | **开局钩子** |
| `Combat.CampaignManager.CampaignEnd()`（private，被 `CampaignDefeated` / `CampaignVictory` 调用） | 结算时填 `cards = 所有玩家卡名`、`relics = 所有遗物名`、`className`，再 `AddCampaignInfo` + `SaveCareerStatistics` | **结算钩子**，且"终局卡组/遗物"是现成的 |
| `Combat.CampaignManager.SerializeCampaignInfo()` | `CampaignInformation` 里带 `campaignStatisticsInfo`、`playerDeck`(CardInfo[])、`playerRelics`(RelicInfo[])、`playerMoney`、`playerHealth`、`playerSpecialStateDicionary` | 续玩后统计仍在，能继续累加 |
| `World.WorldManager.MapEngage(MapNode)` | 玩家进入一个地图节点时调用（内部按 `nodeType` 分流到战斗/商店/休息…） | **逐节点钩子**（唯一需要的"重度"钩子） |
| `World.NewMap.MapNode.node : MapNodeInfo` | `nodeType`（`World.NodeType`：Enemy/Boss/EliteEnemy/RestPoint/Store/Mystery/EmptyNode/SmallGame/Upgrade/Treasure/RemoveCard/TachiEDialogue/ChapterTransition）`nodeID` `isChapterEnd` `possibleEncounterEnemies` `specialIconName` `smallGameName` `nodeColorE` | 路线与"这层可能打谁"都能记 |
| `Combat.GameManager.Update()` | `campaignStatisticsInfo.playedTimeInSecond += Time.deltaTime`（暂停不计） | 时长以游戏自己的计数为准 |
| `UI.PauseMenu.OnAbandonRunClick()` → `new CommandGameOver()` → `CampaignManager.CampaignDefeated()` | **放弃本局也走"失败"这条路** | 必须自己打标记，否则分不清"阵亡"与"放弃" |
| `Career.CampaignStatisticsInfo.GetCareerUpgradeCoinCountByStatistics()` | 官方"本局价值"公式：`节点×0.75 + 普通 + 精英×3 +  Boss×5 + 钓鱼×3`，夹到 0~99 | 直接拿来做"本局收益/评分"，不必另发明 |
| 平台既有件 | `Newtonsoft.Json`（`CapabilitiesDump` 在用）、`UiSkin`、`ModCompendium`（自建画布 + 入口牌子 + 4 标签页 + 分页网格，只在 Main 场景显示） | UI 与落盘都不需要从零造 |

## 3. 功能清单（分三档）

### MVP（先做，可独立验收）
- **一局一行**：日期、职业、结果（胜/败/放弃/中断）、时长、种子、进阶、节点数、本局收益（升级币）
- **详情**：终局卡组（含升级标记）、遗物、骰子特色统计（掷 1 次数 / 掷最大 / 掷最小 / 检定成功·失败 / 钓鱼 / 被紫雾吞噬）、官方计数的击杀构成
- **路线序列**：按顺序列出节点类型（色块），标出 Boss 节点
- **中断识别**：没走到结算就退出/崩溃的局，下次启动标为"中断"

### 完整版
- **逐节点快照**：每个节点的到达时间、当时的 HP / 金币 / 牌堆数 / 遗物数、是否腐化节点、章节
- **逐层获取**：对相邻快照做差分 → 这张卡/这件遗物是**第几个节点拿到的**（对应 STS2 的悬停高亮）
- **每节点耗时**（Run History Plus 的功能）
- **筛选与排序**：按职业 / 结果 / 日期 / 时长（列表页顶部一排按钮，复用图鉴的标签页实现）

### 加分项（不急）
- 导出单局 JSON / 全部 CSV（给作者做平衡分析用，和平台现有的 dump 一致）
- 跨局对比（两局卡组并排）
- 连胜 / 最速纪录页
- 同一 seed 的多局并存（重开 challenge）

## 4. 数据模型

一局一个文件，纯数据、无游戏类型引用（这样游戏更新也不会炸）：

```jsonc
{
  "schema": 1,
  "runId": "20261026-203412-1442534115",   // 开局时间 + seed
  "startedAt": "2026-10-26 20:34:12",      // 来自 playedDate
  "seed": 1442534115,
  "className": "naifrog.milk_frog",        // 原版职业是 CardDateCollection 名
  "ascensionLevel": 0,
  "result": "win|lose|abandon|interrupted|in_progress",
  "durationSeconds": 1234.5,               // playedTimeInSecond（暂停不计）
  "resumedCount": 1,                       // 续玩次数
  "nodes": [
    {
      "index": 1,
      "at": "2026-10-26 20:35:02",
      "sincePrevSeconds": 50.1,
      "nodeType": "Enemy",
      "nodeID": "…",                        // MapNodeInfo.nodeID
      "chapter": 1,
      "corrupted": false,
      "hp": 68, "maxHp": 80,
      "gold": 42,
      "deckSize": 10,
      "relicCount": 2,
      "newCards": ["naifrog.milkfrogstrike"],
      "newRelics": []
    }
  ],
  "final": {
    "deck": ["naifrog.milkfrogstrike+1", "Dice"],   // 升级态用 "+1" 后缀（与游戏内部名区分）
    "relics": ["naifrog.milk_frog_talisman"],
    "hp": 41, "maxHp": 80, "gold": 210,
    "stats": { "normalEnemySlainCount": 23, "eliteSlainCount": 4, "bossSlainCount": 2,
               "travelNewNodeCount": 31, "rollTheOneDiceCount": 3, "rollMaxNumberCount": 12,
               "rollMinNumberCount": 9, "checkSuccessCount": 17, "checkFailCount": 5,
               "fishCount": 2, "catchByPurpleMistCount": 1 },
    "upgradeCoins": 57
  }
}
```

索引文件 `index.json`（列表页只读它，避免打开面板时解析 200 个大文件）：

```jsonc
{ "schema": 1, "entries": [ { "runId": "…", "startedAt": "…", "className": "…",
  "result": "lose", "durationSeconds": 1234.5, "seed": 1442534115, "nodes": 31,
  "ascensionLevel": 0, "upgradeCoins": 57, "file": "runs/20261026-203412-1442534115.json" } ] }
```

## 5. 采集点（5 个钩子）

| 钩子 | 类型 | 写什么 | 失败处理 |
|---|---|---|---|
| `CampaignManager.NewGameLaunchInitialize` | Postfix | 建 `in_progress` 记录 + 索引条目 | 只记日志 |
| `CampaignManager.DeserializeCampaignInfo` | Postfix | 按 `seed` 找回记录，`resumedCount++`，状态回 `in_progress` | 找不到就重建一条（旧版本没记过） |
| `WorldManager.MapEngage(MapNode)` | Postfix | 节点事件 + 快照 + 与上一快照差分出 `newCards/newRelics` | 只记日志；**不写盘**，先进内存队列 |
| `CampaignManager.CampaignEnd`（private） | Postfix | 结算：结果、终局卡组/遗物、统计、升级币，然后 flush 落盘 | 落盘失败只记日志 |
| `UI.PauseMenu.OnAbandonRunClick` | Prefix | 打 `abandon` 标记 | 只记日志 |

补充规则：

- **落盘时机**：只在"节点切换"和"结算"两处 flush；战斗/结算动画期间不碰磁盘。
- **中断判定**：启动时扫索引里所有 `in_progress`；若游戏没有对应的 campaign 存档（或存档里的 `seed` 不匹配）→ 标 `interrupted`。**注意**：不要为此去读 CampaignSave.xml（格式随版本变），改成"启动时若该 runId 对应的记录超过 N 天仍 in_progress 且当前没有活动战役"就标中断，或者在 `NewGameLaunchInitialize` 时把上一条 `in_progress` 标成 `interrupted`（更简单也更准：新局开始 ⇒ 上一局必然已经结束）。
- **续玩同一局**：`DeserializeCampaignInfo` 是唯一入口（`InGameTransit` 不走它），按 seed 归并，不产生第二条记录。
- **放弃 vs 阵亡**：两者都进 `CampaignDefeated`，只有 Prefix 标记能区分。
- **幂等**：所有写入以 `runId` 为键；重复钩子（多场景/重进）只更新不重复追加。

## 6. 存储

| 项 | 决定 | 理由 |
|---|---|---|
| 路径 | `<游戏根>/BepInEx/RunHistory/`（`runs/*.json` + `index.json`） | 独立插件自己的目录；**不写** `LocalLow/.../Save/`，避免污染存档与 Steam 云 |
| 写盘 | 先写 `*.tmp` 再 `File.Replace/Move` | 崩溃时不会留下半截 JSON |
| 上限 | **不限**（`MaxRuns` 配置位默认 0）；索引只读，面板加载与局数无关 | 数据不参与同步，云同步膨胀的顾虑不成立 |
| 版本 | 每个文件带 `schema`；索引损坏可全量重建 | 游戏/更新后仍可读旧记录 |
| 大小估算 | 一局 ~8–30 KB（带逐节点快照） | 一千局约 10–30 MB |
| 读失败 | 单条解析失败跳过并记警告，不阻塞面板 | 用户可能手工改过文件 |

## 7. 展示层

复用平台已经跑通的模式（`ModCompendium`）：**自建 WorldSpace 画布（sortingOrder 1000）+ 桌面场景（Main）里的入口牌子 + 自建面板**。

- 入口："模组图鉴"旁边再放一块「**战绩**」牌子（同一个画布、同一套 `UiSkin`）。
- **列表页**：每页 8–10 行，一行 = `日期 · 职业 · 结果色块 · 时长 · 种子 · 节点数 · 收益`；顶部一排筛选按钮（全部/胜/败/中断 + 按职业循环切换），底部翻页（照搬图鉴的 prev/next/close）。
- **详情页**：上半屏摘要（大标题 = 职业 + 结果 + 时长 + 种子），中部路线条（节点类型色块序列，Boss 加边框，腐化节点标红），下半屏三个分页：卡组 / 遗物 / 统计。卡组用图鉴现成的卡面 slot（含升级态与缩略图；mod 卡直接走 `CardSo`）。
- **悬停高亮**（完整版）：鼠标移到某张卡上 → 路线条里高亮它被拿到的那个节点；数据来自快照差分，不需要额外采集。

**需要的重构**：`ModCompendium` 现在把画布/入口/分页/皮肤都写在自己一个文件里（1500+ 行）。建议先抽出 `ModPanel`（画布 + 入口牌 + 分页 + 关闭）三个公共件，图鉴与战绩共用；否则第二个面板会把同样的 400 行再复制一遍。

## 8. 不变量（硬约束）

1. **只读游戏状态，不写游戏存档**；不参与任何战斗/结算逻辑。
2. 所有钩子 `try/catch`，异常只记日志 —— 平台纪律：接缝边界 FailOpen。
3. 战斗与结算动画期间**不做文件 IO**。
4. mod 内容被卸载后，旧战绩仍可显示（存的是原始 id，显示时再查本地化；查不到就显示 id）。
5. 记录体积有硬上限，且面板只在桌面场景构建（避免战斗帧开销）。
6. 不改变任何原有统计口径（`CareerStatisticsPackage` 照旧由游戏自己写）。

## 9. 实施步骤（建议 4 个提交，每步可独立验收）

| 步 | 内容 | 验收方式 |
|---|---|---|
| S1 | 数据层：5 个钩子 + `RunRecord` 模型 + 原子写 + 索引 + 中断判定 | 玩一局 → 看 `ModKitData/RunHistory/` 里的 JSON 字段是否正确；日志打 `战绩：已记录 …` |
| S2 | 抽 `ModPanel` 公共件，图鉴改为复用（回归：图鉴不退化） | 进图鉴点一遍，行为与之前一致 |

| S4 | 详情页（摘要 + 路线 + 卡组/遗物/统计 + 悬停高亮） | 与游戏内实际卡组/遗物逐项核对 |

## 10. 已定（2026-10-26 拍板）

1. **做成独立 mod**（不并入平台）。实现形态是 **BepInEx 插件**，理由：本 mod 钩的是游戏内部流程、不含任何内容；`ModKit.Api.IMod` 入口契约虽然写在 API 里，但平台侧**从未调用过**（全仓无 `IMod` 引用），照它写等于写个不响的铃；独立插件不依赖平台。
2. **带逐节点快照**（`SnapshotNodes=true` 默认），因为路线 / 逐层获取 / 每层耗时三件事共用这一份数据。
3. **不限局数**。原先担心的"云同步被撑爆"不成立 —— 数据落在 `BepInEx/RunHistory/`，不参与同步；面板只读 `index.json`，与文件数量无关。保留 `MaxRuns` 配置位（默认 0 = 不限），由用户自行决定。

代码位置：`examples/runhistory/`，构建脚本 `tools/build-runhistory.sh`，用法见 `examples/runhistory/README.md`。
