## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 能不能做 mod？ | **能，而且条件很好。** 引擎是 Unity **Mono** 后端，脚本是标准托管程序集，可直接反编译成可读 C# 并用 BepInEx + Harmony 在运行时打补丁 |
| 需要改游戏文件吗？ | **不需要。** 全部挂钩点都是托管方法，用 Harmony 运行时拦截即可，保持游戏本体干净（可随时卸载、Steam 校验不会报错） |
| 最大难点 | **内容装配**：卡牌/遗物数据烘焙进 `resources.assets`（1.94 GB），mod 无法直接"新增资源文件"；新内容必须在**运行时用代码构造** ScriptableObject，或从外部 AssetBundle 加载 |
| 最友好的入口 | 游戏是「**字符串 → 类名 → 反射实例化**」的约定式架构，只要提供命名正确的效果类，就能被既有调度逻辑认领 |
| 社区现状 | Nexus Mods 上**只有 1 个** mod：**Dice View**（预览下一个骰子点数，依赖 BepInEx）。⚠️ 早期版本写的「已有 3 个」是**错的**，源自一条 Steam 论坛帖的陈述、未经核对；2026-10-11 由用户更正 |
| 本机缺什么 | 起初缺 .NET SDK 与 BepInEx，**两者现已就位**（SDK 10.0.401 + BepInEx 5.4.23.2 x64）。反编译工具链（ilspycmd 11.1.0）亦已跑通 |

## 1. 引擎与脚本后端判定

这一步决定整个 mod 技术路线，证据如下（全部实测）：

| 判据 | 观测值 | 含义 |
|---|---|---|
| `Diceomancer_Data/Managed/Assembly-CSharp.dll` | **存在**，1.47 MB | 游戏逻辑是标准 .NET 程序集 → **Mono 后端** |
| `Managed/mscorlib.dll`、`System.*.dll` | **存在**（完整 BCL） | Mono 特征；IL2CPP 不会有这些 |
| `Managed/GameAssembly.dll` | **不存在** | 排除 IL2CPP |
| `Diceomancer_Data/il2cpp_data/` | **不存在** | 排除 IL2CPP |
| `Diceomancer_Data/global-metadata.dat` | **不存在** | 排除 IL2CPP |
| `MonoBleedingEdge/EmbedRuntime/mono-2.0-bdwgc.dll` | 7.39 MB | Mono 运行时（Boehm GC），位于**游戏根目录** |
| `Diceomancer.exe` PE Machine | `0x8664` | **64 位** → 需 BepInEx **x64** 版 |
| Unity 版本 | `2022.3.3f1c1 (52938cbb626d)` | 与 BepInEx 5.4.23.x 兼容 |

**技术含义**：`Assembly-CSharp.dll` 是纯托管 IL，既可反编译阅读，也可被 Harmony 在运行时对任意方法做前置/后置/替换补丁，甚至可直接读改私有字段。这是 mod 开发最省力的一类目标（IL2CPP 则需要处理 `global-metadata` 与原生偏移，难度高一个量级）。

## 4. 核心机制 A：字符串 → 类名 → 反射实例化

**这是全游戏最重要的可扩展设计**。所有"内容类型"都不走注册表或工厂映射表，而是**用名字拼出类型名再反射创建**：

| 位置 | 代码 | 拼接规则 |
|---|---|---|
| `Utilities/EffectUtils.cs:40` | `Activator.CreateInstance(Type.GetType(prefix + name)) as EffectBase` | `Effects.Effect{effectName}`；特殊效果为 `Effects.Special.CardEffect.EffectSpEffect{specialEffectString}`；能力效果为 `Effects.Special.AbilityEffect.EffectSpAbility{...}` |
| `Relic/RelicManager.cs:231` | 同上 | `Relic.RelicEffects.Relic{relicName}`，非特殊遗物退回 `Relic.RelicEffects.RelicBase` |
| `Keyword/CardKeyWordUtil.cs:80` | 同上 | `Keyword.CardKeyword{keywordName}`，找不到退回 `Keyword.CardKeyword` |
| `Combat/Character.cs:501` | 同上 | `SpecialState.SpecialStateEffect{stateName}`，找不到退回 `...SpecialStateEffectEmpty` |
| `Story/StoryConsequence.cs:95` | 同上 | `Story.SpecialStory.SpecialStory{specialConsequenceMethod}` |

**内置基础效果共 22 种**（`EffectUtils.EffectStrings`，即 `Effects.Effect*` 里已有的）：

```
DealDamage, Block, Heal, Draw, DrawOneCard, SeekCard, NumberRoll, NumberPlusSub,
DiscardHand, DiscardRandomCards, EffectDiscardOneRandomCard, ApplyAbility, AddCard,
AddMana, SpImprovise, LoseLife, ChangeMaxHealth, SubtractAllNumber,
ChangeMaxManaCount, AddPower, DoNothing, SpecialEffect
```

`EffectBase`（`Effects/EffectBase.cs`）是 `abstract` 基类，可覆写面干净：

```csharp
public abstract class EffectBase : IPopDescribe {
    public virtual int  GetRNumberCount();
    public virtual string GetEffectDesKey();
    public virtual bool GetCauseBusy();
    public virtual void EffectInitialize();
    public virtual void EffectRemoved();
    protected virtual UniTask ApplyEffectForTarget(Character targetCharacter);
    public virtual async UniTask TriggeredApplyEffect(TriggerBase trigger);
}
```

### ⚠️ 关键坑（必须先知道的）

`Type.GetType("...")` **不带程序集限定名**时，.NET 规范是仅在**调用方程序集 + 核心库**中查找。也就是说：

- 把 `Effects.Special.CardEffect.EffectSpEffectMyCard` 放进你自己的 `MyMod.dll`，**不会被游戏找到**（因为查找发生在 `Assembly-CSharp` 里）。

**✅ 已实机确认（2026-10-11）：Mono 对未限定名 `Type.GetType` 没有任何跨程序集回退。**
所以必须接管这次查找，不能指望反射自己找到你写的类。

**实际采用的稳妥做法**：Harmony **Transpiler 就地替换** —— 把游戏那几个内容工厂里的 `Type.GetType(string)` 调用**原地换掉**，改成平台自己的解析器（它会搜索全部已加载程序集）。实测接管 **4 个内容工厂、共命中 7 处**调用。

> **⚠️ 实现上的一条硬约束**：Transpiler 里**必须在原指令对象上就地改** `opcode` / `operand`，
> **不能新建一个 `CodeInstruction` 顶上** —— 新对象不携带原指令的跳转标签，
> 在 Mono 下会**直接中止进程**（不是可捕获的异常，极难排查）。

> 附带发现：`CardDataManager.GenerateCardPathsDictionary()` 在出厂版里**从未被调用**（死代码），且它引用的是编辑器路径 `Assets/Resources/ScriptableObjects/Cards`。说明开发方留了编译期专用代码在正式包里，可读性上属于"能看出开发痕迹"的点。

## 5. 核心机制 B：内容数据流（为什么不能直接加资源文件）

```csharp
// GameData/CardDataManager.cs:55  —— 卡牌
CardDataSo[] array = Resources.LoadAll<CardDataSo>("ScriptableObjects/CardDataBase");

// GameData/RelicDataManager.cs:31  —— 遗物
Resources.LoadAll<RelicDataSo>("ScriptableObjects/Relics/");

// GameData/AbilityDataManager.cs:29 —— 能力
Resources.LoadAll<AbilitySo>("ScriptableObjects/Abilities/StandardAbilities/");

// World/WorldManager.cs:837-839 —— 敌人遭遇 / 背景 / 剧情
Resources.LoadAll<EncounterEnemySO>("ScriptableObjects/EnemyEncounter");
Resources.LoadAll<BackGroundBase>("ScriptableObjects/BackGround");
Resources.LoadAll<StorySo>("ScriptableObjects/Stories");
```

`Resources.LoadAll` 读取的是**烘焙进 `resources.assets` 的 Unity Resources 容器**。运行时**无法向这个容器追加资源**（Unity 不提供该 API）。

**因此新增卡牌/遗物的两条可行路径**：

1. **纯代码构造**（推荐起步）：`ScriptableObject.CreateInstance<CardSo>()`，用反射写入私有字段 `cardInfo`（`CardInfo` 是 `struct`，通过 `CardSo.CardInfo` 只读属性取到**深拷贝**，所以必须改私有字段或走 `cardSo.cardName` + 内部字段路径）。卡面图可先用现成 Sprite 或纯色/占位图，零美术也能跑通逻辑验证。
2. **外部 AssetBundle**：在 Unity 工程里把自己的 `CardSo` 打成 AssetBundle，mod 启动时 `AssetBundle.LoadFromFile` 读入（需匹配 Unity 2022.3.3 版本），再注入上表的管理器。适合要**自定义卡面美术**的正式 mod。（2026-10-14 更新：ModKit 实现的是更轻的第三条路 —— 运行期从 mod 目录读 PNG，`Texture2D.LoadImage` + `Sprite.Create` 后直接写 `CardSo.cardArt`；游戏侧只消费 `cardArt.texture`，无需 AssetBundle。）

**注入时机**：`CardDataManager.Awake()` 里调用的私有方法 `InitializeData()` 就是注册点。Harmony 对它打 **Postfix**，用反射把 `ScriptableObject` 塞进私有字典：

```
_cardDateCollectionDictionary        (string → CardDateCollection)
_allInGameCardSoDictionary           (string → CardSo)   ← 主表，GetCardSoByName 查它
_allInRandomPoolGameCardSoDictionary (string → CardSo)   ← 随机池（能否被抽到看它）
_colorCardDateCollections / ...UnLocked
```

只进主表不进随机池，卡就"存在但抽不到"——这是个很容易踩的坑。

**兜底**：`CardDataManager.GetCardSoByName(string)` 查不到会打印 `"{name} is not found in CardDataManager"` 并**退回 "EmptyCard"**。所以卡名拼错不会崩溃，而是**静默变成空卡**——调试时务必盯日志。

**数据模型**：`CardSo`（UnityEngine.Object，资产层）→ `CardInfo`（`struct`，逻辑层：`cardName` / `rarity` / `cardColorEs` / `cardManaCostColorEArrays` / `cardKeyWordInfos` / `cardEffectInfos` / `cardUpgradeInfo`）→ `CardEffectInfo` → `EffectInfo`（`effectName` / `specialEffectString` / `effectTargetEnum` / `isPositive` / `effectNumberInfos` / …）。

## 6. 核心机制 C：战斗执行管线

`Command` 命名空间是**指令/子指令双层结构**：

- 接口与调度：`ICommand`、`PlayerCommandHandler`、`CommandCommonUniTask`、`SubCommand`
- **36 个顶层指令**：`CommandCastCard`、`CommandResolveCard`、`CommandEndTurn`、`CommandStartBattlePhase`、`CommandBattleOver`、`CommandEnemyDeath`、`CommandGainRelicByInfo`、`CommandRemoveRelic`、`CommandRest`、`CommandSmallGame`、`CommandWorldPhase`、`CommandMoveToNewChapter`、`CommandPlot`、`CommandTriggeredRelic`、`CommandTriggeredAbility`、`CommandSpecialStateResolve`、`CommandGameOver`、`CommandVictory` …
- **约 50 个 `SubCommand*`**：`SubCommandDealDamage`、`SubCommandDrawOneCard`、`SubCommandDiscardCard`、`SubCommandAddCardToPlayer`、`SubCommandAddMana`、`SubCommandChangeRNumber`、`SubCommandChangeCardPlace`、`SubCommandUpgradeCards`、`SubCommandSetCardByInfo`、`SubCommandCopyStackCard`、`SubCommandOrganismSpawn`、`SubCommandChangeUI` …

**为什么这层对 mod 特别友好**：

- 每个动作是**独立类**，要加一个新动作不必改大函数，注入 `ICommand` 实现即可。
- `PlayerCommandHandler` 是**控制台/沙盒类 mod 的天然入口**（加删改卡牌、自定义掉落池、控制台指令都可以挂在这一层；结构适合，但目前没有任何 mod 用过它）。
- 指令是 `UniTask` 异步链，mod 的异步动作能自然接入既有排队/动画时序。

## 7. 核心机制 D：存档系统

`SaveLoad/SaveLoadManager.cs`：

| 项 | 值 |
|---|---|
| 目录 | `Application.persistentDataPath + "/FULLVERSAVE/"` 与 `"/SYSTEMSAVE/"` |
| Windows 实际路径 | `%USERPROFILE%\AppData\LocalLow\UltraPiggyStudio\Diceomancer\` |
| 序列化器 | **Sirenix Odin** `SerializationUtility.SerializeValue(obj, DataFormat.JSON)` |
| ⚠️ 命名陷阱 | 内容其实是 **JSON**，但文件名后缀是 **`.xml`** |
| 文件 | `WorldSave.xml`、`CareerSave.xml`、`CareerStatisticsSave.xml`、`SystemSave.xml`（JSON）；`CampaignSave.xml` 例外，用 **`DataContractSerializer`** 生成**真 XML** |
| 安全写入 | `Temp*` → `File.Replace` → `BackUp*`（自带备份轮转，`CareerSave` 等走这条） |
| 版本字段 | `WorldSaveVersion`、`campaignSaveVersion`/`careerSaveVersion`/`systemSaveVersion` 均为 `"1.0.0"`，不匹配只打日志不阻断 |
| 另有玩家文件 | 自定义法术力颜色：`persistentDataPath/customColors.json`（`UI.ManaCustomColor/ManaColorManager.cs:133`） |

**mod 含义**：种子类 mod 需要在**开局写档前**介入（否则达到不了"同一局"目的）；沙盒类 mod 直接改内存态数据比改文件更安全（文件是整体序列化，手改易崩）。做存档相关 mod 时**务必先备份** `FULLVERSAVE/`，因为 `CampaignSave.xml` 解析失败会触发 `CheckSaveVersionAndRemoveInvalidSave()` **直接删除 `CampaignSave.xml` 与 `WorldSave.xml`**。

## 8. Mod 可行性结论与推荐路线

### 推荐：BepInEx 5 (Mono, x64) + HarmonyX

```
优点：不改游戏文件、可插拔、社区已有同类成果（Nexus 上仅 1 个：Dice View）
版本：BepInEx 5.4.23.2 x64（已验证下载地址可达，HTTP 200）
装法：解压到游戏根目录，首次启动生成 BepInEx/plugins + config + LogOutput.log
开发：插件继承 BaseUnityPlugin，[HarmonyPatch] 打补丁，编译为 net472/netstandard2.0 类库
```

### 三种 mod 形态与难度

| 形态 | 例子 | 难度 | 关键挂钩 |
|---|---|---|---|
| **运行时行为修改** | 骰子显示下一个值、伤害倍率、无限法力 | ★ 低 | 直接 patch 对应方法，无需新内容 |
| **UI/HUD 增强** | 显示隐藏信息、数值预览、伤害计算器 | ★★ 中 | patch UI 管理器 + 自建 Canvas |
| **新增内容** | 新卡、新遗物、新关键词、新敌人 | ★★★ 高 | 反射工厂 + `InitializeData` 注入 +（要美术则）AssetBundle |

## 10. 社区已有成果（已更正）

**Nexus Mods 上只有 1 个 mod：Dice View —— 预览下一个骰子点数（依赖 BepInEx）。**

> ⚠️ **更正记录（2026-10-11）**：本报告早期版本写的是「已有 3 个 mod：Dice View / SeedChanger / SandboxTool」，
> 来源是一条 2025-01 的 Steam 论坛帖里的陈述（「Currently there are 3 mods in Nexusmods」），**未经核对即被采信**，
> 还被写进了设计文档和 Mod 研发线结论。用户核对 Nexus 后确认：**后两个 mod 并不存在**。
> 教训：社区帖里的数量与名称属于二手陈述，不能当事实用；能核对就必须核对（Nexus 本身有 Cloudflare 拦截，403）。

**意义（与原判断相反）**：这款游戏发售两年，Nexus 上只有一个「读一个数值并显示」的浅层 mod。
这与本报告其余部分的技术结论互相印证——深层内容创作要同时对付运行时反射工厂、
烘焙进 `resources.assets` 的资源、运行期注入且必须标 `Smart` 的本地化表，以及一堆静默降级，
对普通 modder 的成本过高。所以「路线已被他人验证」这个说法**不成立**：唯一可参照的样本只有 Dice View 一个。

## 12. 风险与注意事项

1. **版权**：反编译仅用于本地学习与个人 mod 开发；**不得再分发游戏本体资源**（贴图、音频、数据资产）。发布的 mod 宜只含自己的代码，并在说明中要求用户自备游戏。
2. **联机/成就**：`SteamManager` 存在，改内存可能影响成就判定，需自行评估。
3. **存档安全**：`CampaignSave.xml` 解析失败会导致游戏**自动删除存档文件**——测试 mod 前先备份 `FULLVERSAVE/`。
4. **版本脆弱性**：Harmony 补丁绑定方法签名，游戏更新后可能失效（表现为启动报错或静默失效）。建议给 patch 加 `try/catch` 与版本检测。
5. **原先的三条未验证项，现已全部有结论**：
   - Mono 对未限定名 `Type.GetType` **没有**跨程序集回退 → 必须用 Transpiler 接管（见 §4）；
   - `BepInEx 5.4.23.2` 在本版本 Unity 上**加载稳定**（ModKit 已在其上跑通完整实机验收）；
   - `CardSo` 私有字段的反射写入**没有被 `OnValidate` 覆盖**（克隆 + 反射装配已实机生效）。
