# DICEOMANCER Mod 平台（ModKit）· 平台设计

> **状态：已建成，并通过实机验收（2026-10-11）。**
>
> 本文记录平台**要做成什么样、实际做成了什么样、以及为什么这么做**。
> 想知道怎么用平台做 mod，请看《ModKit-作者手册》——不是这一份。
>
> 早期那条试验线（`DiceomancerMod.dll`）已被本平台取代，其文档《Mod开发指南》已删除；
> 其中仍然有效的三条踩坑已并入本文 §7。

---

## 1. 这个平台要解决什么问题

**目标**：让 mod 作者**不需要理解游戏内部运行逻辑**，只用平台接口就能做内容。

**判断标准**（也是验收标准）：一个作者能否只靠《作者手册》，
在不读任何反编译代码的前提下，做出一张卡、一件遗物、一个能力，并让它们在游戏里真实生效。

**非目标**（明确不做，避免范围失控）：

| 不做 | 原因 |
|---|---|
| 打包好的美术资源包（Unity 工程 / AssetBundle） | Q2（2026-10-14 更新）：卡面可用 mod 自带的 PNG 覆盖，但不需要 Unity 工程 |
| 运行期脚本（Lua / JS / 运行期编译 C#） | 决策 Q1：数据化 + C# 兜底 |
| 修改游戏本身的资产与数值 | 「不动资产」的硬约束：平台全程只读游戏目录 |
| 与其它同样改类型查找的 mod 共存 | 冲突检测见 §8 |

## 2. 平台在技术上的三个支点

平台能做起来，靠的是三件**此前已经实证过**的事，不是设计上的一厢情愿。

### 支点一：游戏的类型查找方式是可以被接管的

游戏找内容类的统一做法是「把名字拼成字符串 → 查类型 → 造实例」。

**关键问题**：那个查找原本**只能看到游戏自己的程序集**，看不到 mod 的类；
而且**找不到时不报错**——只是安静地什么都不发生。

**平台的解法**：在启动时**装一个桥**，把游戏里那几处查找替换成平台自己的版本，
后者会搜索**全部已加载的程序集**。

> **这一条是整个平台的地基。** 没有它，作者写的任何 C# 类都找不到，
> 而且失败是静默的——这正是本平台要消灭的那类失败。

**实测**：桥接管了 **4 个内容工厂**（效果、关键词、遗物效果、特殊状态），共命中 **7 处**查找调用。

### 支点二：原版内容可以整份克隆

游戏的内容数据（卡牌、遗物、能力……）是**烘焙进资产包**的，
**运行期无法追加新资产**——这是 Unity 的硬限制。

**平台的解法**：**克隆一份原版内容对象**（连同图标、动画、字段布局），
再把它内部描述「这是什么内容」的那部分改写成作者要的值。

这样作者**不需要提供任何美术资源**，外观直接借原版的。（2026-10-14 更新：卡面可用 mod 自带的 PNG 覆盖，见 §3.2 Q2 与《作者手册》§3.4。）

### 支点三：验收可以是机械的

平台不依赖「看着没问题」，而是依赖可复跑的机械判据：

| 判据 | 内容 |
|---|---|
| 构建 | 每个程序集独立编译，退出码 0 |
| 规则断言 | 76 条，覆盖校验、失败隔离、跨程序集解析、各类内容 |
| 工具链黑盒 | 11 条，跑真实命令行 |
| 资产闸门 | 游戏资产逐文件哈希比对，退出码 0 |
| 读回自检 | 写完的内容用**游戏自己的接口**读回来验证 |

## 3. 三条设计原则与三个决策

### 3.1 原则

| 原则 | 含义 | 作者看到的结果 |
|---|---|---|
| **P1 概念暴露，类型不暴露** | 只暴露稳定的游戏概念，不暴露会随版本漂移的内部类型 | 接口里没有 `CardSo` / `CardInfo` / `EffectInfo` 这些名字 |
| **P2 默认数据化，代码兜底** | 常见需求写 JSON；表达不了的才写 C# | 15 个内置语义 + 可选的自定义效果类 |
| **P3 平台吸收全部脏活** | 克隆资产、接管查找、灌文案、失败隔离全在平台内 | 作者只管描述「我想要什么」 |

**一句话判据**：mod 作者**永远不应该**为了写一个 mod 而阅读 `research/decompiled/` 里的任何文件，
也不应该知道什么是 Harmony、`Type.GetType`、`[SerializeField]`。

### 3.2 决策记录（已确认）

| 编号 | 问题 | 决策 | 理由 |
|---|---|---|---|
| **Q1** | 脚本模型 | **数据化 + C# 兜底**；不引入 Lua/JS，不做运行期编译 | 运行期编译在这套 Mono 环境下风险高、体积大；C# 兜底已足够表达 |
| **Q2** | 美术来源 | **只借原版资产**（`artTemplate` 只接受原版名字） | 外置美术需要 Unity 工程与 AssetBundle，且涉及「素材不得来自游戏本体」的合规红线。<br>**2026-10-14 更新**：卡牌新增可选字段 `art`（相对 mod 目录的 PNG/JPG，运行期 `Texture2D.LoadImage` + `Sprite.Create` 直接写入 `CardSo.cardArt`，无需 AssetBundle 与 Unity 工程）；`artTemplate` 仍是必填的模板来源，动画/tooltip 依旧继承模板。 |
| **Q3** | 首版范围 | **全部内容类型** | 卡牌 / 遗物 / 文案 / 关键词 / 能力 / 剧情后果 |

**Q3 的诚实执行方式**：用户要求全都要，接受；
但**交付顺序按实证状态分层**，绝不把「未验证」当成「已验证」对外承诺
（认知纪律 C9：**未做 ≠ 已验证**）。实际结果见 §6。

## 4. 实际架构

平台是**四个程序集 + 一套工具 + 一个插件**。分层的目的是让一条规则可机械检查：

> **只有最底下那一层可以引用游戏程序集。**

这条规则不是自我约束，而是**被构建脚本机械断言的**——上层代码一旦引用游戏类型就直接编译失败。

| 层 | 目录 | 职责 | 能引用游戏吗 |
|---|---|---|---|
| 契约层 | `ModKit.Api` | 作者可见的全部契约（JSON 定义、效果上下文、特性） | ❌ 只能引用基础库 |
| 核心层 | `ModKit.Core` | 解析、校验、加载、注册表、命名表 | ❌ 不含任何游戏类型 |
| 游戏层 | `ModKit.Game` | 克隆资产、装配、桥、本地化注入、重建守卫、各种探针 | ✅ **唯一** |
| 测试层 | `ModKit.Tests` | 76 条规则断言（含一个测试用 mod） | ❌ |
| 工具 | `ModKit.Tools` | 命令行 `new` / `lint` / `pack` | ❌ **不需要游戏也能跑** |
| 插件 | `ModKit.Plugin` | 游戏内入口（BepInEx 插件 + 配置项） | ✅ |

配套目录：`modkit/mods/`（示例 mod）、`modkit/schemas/`（JSON 模式）、`modkit/tools-tests/`（工具链黑盒测试）。

> **对照上一版设计**：原计划叫 `ModKit.Runtime` / `ModKit.Loader`（L2/L1）。
> 实际落地时按「能不能引用游戏」这条规则重新切分成了 `Core` / `Game` / `Plugin`——
> 切分依据更机械，也更容易被构建脚本守卫。

### 4.1 插件启动后的流水线

顺序是**有意义**的。第 4 步的位置曾经出过一个很典型的 bug：

1. **建注册表** —— 扫描程序集，把作者写的自定义类登记进索引；
2. **装渲染探针** —— 挂钩卡牌渲染，用来断言「游戏真的把我们的卡显示出来了」；
3. **加载 mod 文件** —— 解析、校验、逐条隔离错误；
4. **注入文案** —— **必须在装配之前**；
5. **装配内容** —— 克隆模板、写入字段、注册进游戏数据库；
6. **读回自检** —— 用游戏自己的查询接口把刚写进去的东西读回来验证。

> **为什么文案必须在装配之前**：装配过程**会读取**文案
> （卡牌被创建时就会去查它的名字）。顺序反了会表现为「卡面显示一串 key 名」，
> 而且描述模板还会抛异常。
>
> **一般化的教训：写文字的操作，必须排在任何会读这些文字的操作之前。**

### 4.2 把「静默失败」变成「加载期报错」

游戏的一大特点是**命名写错时不报错**：

| 场合 | 游戏原本的行为 |
|---|---|
| 关键词类名写错 | 静默退回基类 → **没有任何行为** |
| 效果类名写错 | 找不到类 |
| 触发点写错 | 安静地永不触发 |
| 能力取不到 | 直接崩溃（那个 `null` 检查是假的） |

平台把这四类全部变成**加载期就报错，并告诉作者正确的名字应该是什么**。

**这是平台最主要的价值来源**——它把作者从「进游戏反复试」里解放出来。

### 4.3 平台吸收掉的脏活（作者完全不用知道）

| 脏活 | 不做会怎样 |
|---|---|
| 克隆原版内容对象 | 作者要自己做美术与资产 |
| 接管类型查找（桥） | 作者的 C# 类找不到，且静默失效 |
| 把文案灌进本地化表，并置上「智能格式」标记 | 卡面显示 key 名；`{数字}` 占位符抛异常 |
| **游戏会重建数据容器 → 平台自动重注册** | 内容在某次加载后**整体消失** |
| 统一同步 / 异步接口的差异 | 作者要自己判断哪个 API 会入队 |
| 「构造即入队」的副作用去重 | 作者的重复调用会重复执行 |
| 逐条失败隔离 | 一处笔误整包失效 |
| 读回自检 | 「写进去了」和「取得到」是两件事，后者才算数 |

> **关于第 4 条**，这是**踩了三次**的同一类缺陷：
> 游戏会在若干时机**重建**它的内容容器，平台注册进去的东西被**无声抹掉**。
> 最终方案是在那几个重建点挂钩，重建之后自动**重放注册动作**。

## 5. 平台的诚实机制

平台有一个与功能同等重要的设计目标：**不谎报自己的状态**。

### 5.1 内置语义的「实证档位」

每个内置效果语义都带一个档位，作者能看到它处于哪一档：

| 档位 | 含义 | 作者该怎么理解 |
|---|---|---|
| ✅ **已实机验证** | 在真实游戏里跑通过 | 可以放心用 |
| ⚠️ **已实现未验证** | 平台按游戏接口实现了，但没跑过 | **可以用，当成试验性** |
| 🚫 **不支持** | 机制不存在或探针未通过 | **不得对外承诺** |

档位表**写在代码里**，lint 按它给作者打警告，《作者手册》也照它写。
这样「代码认为的档位」与「文档承诺的档位」不会各说各话。

### 5.2 读回自检

平台写完内容后，会**用游戏自己的查询接口把它读回来**。

> **为什么要多这一步**：早先版本的「写入 N 条」统计的是**自己调了几次写入**——
> 那只证明自己动过手，不证明游戏真的认。
> 加了读回之后，同一批日志立刻暴露了真实情况。
>
> **一般化的教训：要断言 A 对 B 做了某事，就得去读 B，而不是把 A 重算一遍。**

### 5.3 一次真实的翻车（保留，因为它有代表性）

平台曾把「已本地化」判定为通过，而卡面上实际显示的是
**`No translation found for ...`**。

原因：探针用的是**平台自己的两参数查询**，而游戏用的是**另一个重载**。
两边条件不同，于是探针报了成功。

修法不是调整判定，而是**改成去读卡面上真实渲染出来的那段文字**。

## 6. 验收记录（数字统一收敛在这里）

**平台已通过实机验收**（2026-10-11，从存档基线启动，由玩家实际操作）。

### 6.1 机械基线

| 项目 | 结果 |
|---|---|
| 构建 | **6 / 6 退出码 0** |
| 规则断言 | **76 / 76 通过** |
| 工具链黑盒 | **11 / 11 通过** |
| 资产闸门 | **退出码 0**（游戏资产零改动） |
| 示例 mod 严格 lint | **通过**（0 错误） |

### 6.2 逐内容的实机结果

| 内容类型 | 档位 | 实机证据 |
|---|---|---|
| **卡牌** | ✅ | 「木盾」「稳手」「护盾强化」拿到 / 打出 / 结算是真的；卡面中文名与费用正确 |
| **遗物** | ✅ | 「石手环」出现、描述正确、**触发与效果都真的生效**（获得 3 格挡） |
| **能力** | ✅ | 「护盾提升」由卡牌施加、悬浮提示正确、**效果真的生效** |
| **文案** | ✅ | 卡面名 / 能力描述 / 遗物名全部正确显示 |
| **自定义 C# 效果** | ✅ | 平台第一条走通的自定义效果（「获得格挡时额外 +X」） |
| **关键词** | ⚠️ | 已实现，**未实机验证** |
| **剧情后果** | ⚠️ | 内建类型纯数据可用；`"Special"` 分支走未接管的工厂且失败静默 → 如实标注不支持 |
| 其余 12 个内置语义 | ⚠️ | 已实现，**未实机验证** |

### 6.3 本次验收中最有价值的发现

平台在「能力」这条链路上暴露了一个**赋值顺序**问题，值得单独记下：

> 游戏创建能力效果时，**先生成效果对象、再给它写名字**。
> 而平台的效果类要在「生成」这一步做登记——**那一刻名字还是空的**。
> 按名字登记会**静默失败**（不报错，只是不生效）。
>
> 修法：改成按**对象本身**登记，绕开对赋值顺序的依赖。

**一般化**：**依赖某个字段已就绪之前，先去读那段代码的赋值顺序。**
「创建期回调」尤其危险——宿主对象往往还没被填完。

## 7. 三条仍然有效的踩坑（原《Mod开发指南》幸存内容）

早期试验线虽然停了，但下面三条对**任何在本副本上做 mod 的人**都仍然有效：

### 7.1 游戏副本根目录必须有 `steam_appid.txt`

内容为 `2501600`。没有它，Steam 的启动检查会让这个副本**大约 10 秒后自动退出**。

### 7.2 接管类型查找时，必须「就地修改指令对象」

替换游戏方法里的查找调用时，**不能在原指令基础上新建一个指令对象**——
那样会丢掉它携带的跳转标签，在 Mono 下会**直接中止进程**，
而不是抛出一个可以捕获的异常（于是极难排查）。

### 7.3 运行时注入的文案必须标记为「智能格式」

否则 `{数字}` 这类占位符会被当成 `String.Format` 处理并抛异常，
而且**游戏日志里看不到任何错误**，只表现为一个弹窗。

平台把这一条写死在注入流程里，作者**不需要也无法关掉它**。

## 8. 风险与合规

### 8.1 分发红线

| 红线 | 说明 |
|---|---|
| 反编译产物**仅供本地学习** | 不再分发 |
| **不得再分发游戏本体资源** | 包括反编译产物与重编译出来的 DLL |
| 发布物**只含自己的代码** | 使用者自备游戏 |

### 8.2 平台风险

| 风险 | 现状与缓解 |
|---|---|
| **与其它改类型查找的 mod 互斥** | 平台会**点名报错**而不是静默失败；建议只装平台一个插件 |
| **游戏版本升级可能使桥失配** | 桥按方法签名定位，签名变了会装不上；平台会把失败报出来 |
| **未实证的语义可能行为不符** | 用档位标注（§5.1），且不对外承诺 |
| **任意 DLL 都能被执行** | 这是所有 BepInEx mod 的固有前提，平台不额外放宽；文档明确声明 |
| **资产污染** | 平台全程只读游戏目录；改动只在工作区副本；独立于平台的资产闸门逐文件核对 |

## 9. 已知边界与未做的事（诚实清单）

**已明确不做**：

- 外置美术资源注入；
- 运行期脚本语言；
- 与其它类型查找类 mod 共存；
- 图形界面的作者工具（只有命令行）。

**功能空洞**：

| 空洞 | 影响 |
|---|---|
| 关键词未实机验证 | 作者用之前需自测 |
| 12 个内置语义未实机验证 | 同上，lint 会标警告 |
| 剧情后果的 `"Special"` 分支未做 | 该分支下的剧情后果无法表达 |
| 显式骰子种类（D4/D8/D12/D20）未支持 | 目前按保守映射处理（`min==max` 退化为固定值，否则按 D6） |
| 能力只暴露了部分控制字段 | 保留规则与延迟仍继承自模板 |
| 「重开一局后内容是否仍在池中」未验证 | 需要一次专门验证 |

**工具链缺口**：

> **`capabilities.json` 是一份手工维护的快照，而且没有「自定义效果清单」这一项。**
>
> 后果：**lint 会对所有 `custom:` 报「未注册」的假错**（`--strict` 必定失败）。
> 运行时是正常的——平台在游戏里是实时扫描程序集的。
>
> **正确修法**：让平台在探测之后**自己写这份快照**，
> 把自定义效果与遗物行为两项也写进去，lint 才能读到真值。

**其它待补**：

- 遗物与能力**缺渲染探针**（目前只挂了卡牌渲染）；
- **跨引用校验缺失**——卡牌指向一个不存在的能力时，会让**卡牌图鉴崩溃**。
  这种错误应该在 lint 或装配阶段就被拦下，而不是等到玩家点开图鉴。
- 手册与本文里提到「能力只暴露部分控制字段」的细节，可再补一张能力字段全表。

## 附：原始设计阶段的推演结论（保留备查）

设计阶段曾就若干问题做过推演，结论与最终实现的对账如下：

| 当时的问题 | 推演结论 | 实际结果 |
|---|---|---|
| 角色侧可调用的战斗 API 是否 public | 是 | ✅ 成立 |
| 费用颜色的合法组合 | 只接受单色；多色「任选」无对应表达 | ✅ 成立（可用单色 6/6） |
| 关键词 / 遗物基类可覆写成员 | 已列出 | ✅ 成立 |
| 骰子取值语义 | 按「骰子种类」而非 min/max | ✅ 成立，故平台做保守映射 |
| 能力 / 剧情后果的工厂能否接管 | 未知，需探针 | ✅ 能力**搭既有便车**（零新增补丁）；剧情后果 `"Special"` 未接管 |

**探针方法**：全库扫描 `Type.GetType(`（共 10 处），逐条判定
「是否按名字拼接 + 桥是否已接管」。这是回答「要不要新增补丁」的唯一依据。
